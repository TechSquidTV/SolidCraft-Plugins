# Fields, manifests and errors

## plugin.json

- Each `runtime.entries[]` is one dialog: `name` (`make-<thing>`), `effect`, `slots` and `input_schema`. Each field has `title` and `type`, and `description`, `default`, `enum`, `minimum`/`maximum` and `unit` where they apply. Give a field a `description` whenever its title doesn't say what to enter.
- `runtime.commands` lists every host command the plugin runs. In screws, inserts, nuts and extrusions a unit test compares it with what the code sends (its own list plus `component::commands()`), so a new command goes in the manifest and that test. A plugin without the test only fails in the host.
- `version` is the workspace version. Catalog-owned `enum` choices are generated by `cargo run -p catalog-tool -- --write`; don't hand-edit them.

Use the shared field names wherever they fit: `size`, `custom_size`, `create`, `placement`, `thread_modeled`. `create` goes through `plugin_kit::create`; `placement` through `place::parse_input`.

`placement` is the one array field an entry has. SolidCraft draws it as a pick field (`x-solidcraft-selection`, accepting `profile`, `sketch_point` and `sketch_curve`) and sends the picks as selection references: a point, a circle, or the inside of a circle, which `place::resolve_all` turns into the circle's centre point so the part still follows the sketch; the plugin never reads the app's selection to place a part. The dialog turns Run off for any other array or keyword, which `every_package_declares_the_placement_pick_field` in `place.rs` checks.

## Parsing

Start `parse` with `input::workflow_fields(v, include_str!("../plugin.json"), "<entry>")`, which refuses keys the packaged manifest doesn't list. Read each field with `input::choice`, `input::flag`, `input::length_or` or `input::optional_length`, and return `FieldError::new("<key>", "<what to do>")` for a bad value. Refuse in `parse` anything you can know before building, such as holes that overlap or a run over budget, so nothing is half-built.

## Errors

| Starts with | The host |
|---|---|
| `<field_key>: ` | shows it against that field |
| `<command.id>: ` | reports a failed host command |
| anything else | treats it as a trap |

Write the reason as what the user should do: `placement: choose at most 32 points`.

## Breaking field changes

A renamed or retired key is refused, never aliased or given a fallback. List the old key and its replacement under Older field names in the plugin's REFERENCE.md, mark the commit `!`, and add the migration to the release notes.

## Gotchas

- **An entry without `slots` shows its id.** The menu said `make-bearing` until the entry got `"slots": [{"kind": "menu", "name": "Bearing"}]`.
- **A field key in an error must be a field the dialog has.** `parts:` errors showed nowhere; they now use `placement:`.
- **A blank dropdown is its default**, through `input::choice`. Don't treat `""` as an error.
- **The Bearings manifest is within a few bytes of the host's 16 KiB limit.** A longer description there fails `generation_keeps_packages_insertion_only`; shorten another to make room.
- **Line and point ids repeat between sketches.** A pick carries its sketch's feature id; compare sketches by that, not by an id within one.
- **A new entry needs a case in `tests/cli_test.py`.** The Bearings case failed on `main` when `make-csk` was added beside `make-bearing`.
- **`catalog-tool --write` refuses a field the manifest lacks.** Add the field to `plugin.json` first.
